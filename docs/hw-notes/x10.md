# EasySMX X10 (`3537:1023`) — configuration protocol & XInput-on-Linux

Investigation notes for whether the EasySMX X10 can be configured by `padtune`,
and why it will not enter XInput mode when wired on Linux. Provenance tags:

* **HW** — observed on Daniele's X10 on this machine (2026-10-30);
* **WEB** — EasySMX official pages / manuals (see [Sources](#sources));
* **APK** — reverse-engineered from the official EasySMX Android app
  (`com.smx.platform`, see [The app & protocol](#the-app--protocol));
* **INF** — inference, not yet verified.

> **TL;DR** — the X10 is **not** a drop-in for `padtune` and is a **different
> ODM and protocol** from BIGBIG WON. Config does **not** use the USB `0xFF7A`
> vendor channel; the official configurator is an **Android-only app that
> drives the pad over Bluetooth LE** (service `FF00`, write `FF01`, notify
> `FF02`). The on-wire protocol is the **"Kr" protocol** (`com.krly.platform`
> SDK): frames `[len][opcode][content…][SN]`, a ~70-opcode command set — totally
> unlike BIGBIG WON's `A5/A4` + CRC-16/MODBUS. Supporting the X10 means a **new
> BLE transport + the Kr command set** in `padtune`, which fits the main
> session's transport-abstraction goal. The XInput-wired-on-Linux failure is a
> separate firmware/host-handshake issue, independent of configuration.

## USB enumeration (HW)

Three connection paths, all probed read-only with `examples/probe.rs`:

| Path | Enumerates as | Interfaces | `A5/0xFF7A` config iface? |
|---|---|---|---|
| Wired (DInput) | `3537:1023` EasySMX X10 | iface0 gamepad `0001/05`, iface1 `0001/80` + consumer `000c/01`, iface2 keyboard `0001/06` | **No** |
| Wired (XInput) | *unreachable on Linux* — pad stays in DInput | — | — |
| 2.4 GHz dongle | `045e:028e` "Xbox 360 Controller" (vendor-class XInput) | xpad binds it; hidapi sees **no** HID interface | **No** |

`examples/probe.rs -- --all` (read-only `A5` GETs) got "(no reply)" everywhere:
there is no BIGBIG WON `A5/A4` vendor channel on any X10 interface on Linux. The
three-HID-interface resemblance to BIGBIG WON is coincidental — the X10's iface2
is a keyboard, not a config channel.

## The app & protocol

The official configurator is the **Android-only** app `com.smx.platform`
(EasySMX, backend `app.yisuma.cn`), sideloaded from a Google-Drive link (WEB).
It connects over **BLE** to a device named **`QMacro`** (WEB) and does
calibration, key mapping, macros, triggers, sticks, lighting and vibration.
APK decompiled with jadx; protocol lives in the bundled **`com.krly.platform`**
("Kr"/KRLY) SDK. APK saved at
`/home/daniele/Code/ZTool/re/apk/easysmx-x10/` (sha256 in the `.sha256` file);
curated sources under `sources/`.

### BLE GATT map (APK — `com.smx.platform.util.Constants`)

| UUID | Role |
|---|---|
| `0000FF00-0000-1000-8000-00805F9B34FB` | config **service** |
| `0000FF01-…` | **command** characteristic (write) |
| `0000FF02-…` | **notification** characteristic (notify) |
| `0000FF10-…` | firmware **OTA** service |
| `0000FF11-…` / `0000FF12-…` | OTA instruction / OTA data |

Advertised BLE name `QMacro`; the app connects by MAC after a system BT pairing.

### Frame format (APK — `com.krly.platform.kr.request.BaseReq`)

Command written to `FF01`:

```
[len] [opcode] [content…] [SN]
```

* `len` = `content.length + 3` (counts len byte, opcode and the trailing SN);
* `opcode` = one byte from `KrAgreement` (below);
* `SN` = a process-global incrementing sequence byte;
* **no checksum** on normal command frames.

OTA frames instead use a **2-byte opcode** (`[len][op_lo][op_hi][content…]`) and
firmware integrity uses **CRC-16/CCITT** (poly `0x1021`, init `0x0000`, MSB-first;
`Utils.crc`).

Notification/reply on `FF02`: `[len] [opcode] [payload…]`, matched to the
request by opcode (`BaseReq.verifyId`); `payload[0]` is usually a result byte.
Example — `DeviceInfoReq` (opcode `97`/`0x61`) reply: bytes `[2..5]` =
project coding, `[5..8]` = hardware version, `[8..11]` = firmware version.

### Command set (APK — `com.krly.platform.api.KrAgreement`, decimal opcodes)

Identity/status: `97` query device info, `48` device type/platform, `49` query
electric quantity (battery), `132` query device version, `50`/`51` sleep time,
`8` BT host state. Mapping: `80` query mapping key, `13` set key mapping, `29`
set-key-mapping end, `5` reset keyboard, `1` set keyboard mode. Sticks/triggers:
`100` query trigger, `98` query rocker, `120` trigger/rocker calibration,
`85/86/87` calibration start/end/complete, `65/66/67` self-calibration. Lighting:
`74` query / `75` set effect / `76` set mode. Vibration: `101` query / `53` set
level / `69` force test. Macros: `70/71` record start/stop, `72/73` report,
`45/46/47` set macro key/trigger/termination, `55` burst rate, `92/93` profile
num/query, `119/121` macro config, `58/60/61/62/63` sub-keys & rocker. OTA:
`6` enable, `80` ready, `83` complete. Dongle: `96` pairing. (Full list in
`sources/com/krly/platform/api/KrAgreement.java`.)

A per-command `content` encoder exists for each `*Req` class (e.g.
`SetTriggerOrRockerReq.setContent(a,b)` → 2 payload bytes). These are small and
can be transcribed when implementing.

### USB-HID is *possible* but unused by the app (APK + INF)

The Kr SDK also contains `USBManager`: it claims **interface 0**, finds the
**interrupt** IN/OUT endpoints and exchanges the **same 64-byte Kr frames** over
`bulkTransfer`. The EasySMX app never calls it (BLE only), so there is **no
evidence the X10 firmware answers Kr frames over USB in DInput mode** — but it is
a concrete, cheap hardware experiment: write a framed read-only query
(`CMD_QUERY_DEVICE_INFORMATION` → `03 61 <SN>`) to iface0's interrupt OUT and
watch the interrupt IN. If it replies, the X10 becomes configurable over plain
USB hidraw on Linux, no BLE needed. **Needs Daniele's ok** (it writes to the
pad, though only a query).

## XInput-on-Linux failure (HW + INF)

* Mode toggle is a firmware button combo: hold **B + S for 3 s** → XInput (blue
  LED) ↔ DInput (yellow LED), short vibration on success (WEB, X10 manual). No
  physical XInput/DInput switch — only cable/dongle/BT (HW).
* After a firmware update, on Linux the pad **never enters XInput when wired**
  and B+S leaves it in DInput; on **Windows** the same pad goes XInput (HW). Via
  the dongle it *is* XInput (`045e:028e`) because the dongle presents XInput
  itself regardless of host (HW).
* **Hypothesis (INF):** wired XInput is gated on a host handshake the Windows
  xpad/GameInput stack performs and Linux does not (e.g. the Microsoft OS 2.0
  descriptor request or an XInput vendor control transfer); the firmware update
  may have tightened this. Unrelated to the BLE config channel, and likely not
  fixable from `padtune` without firmware RE/reflash.
* **Cheap diagnostic (when X10 reconnected):** hold B+S wired on Linux and watch
  the LED/vibration. LED changes + vibrates → firmware toggles, host
  re-enumeration is the problem (capture with `usbmon`/`dmesg`). Nothing happens
  → firmware not registering the combo. An EasySMX **firmware updater** exists
  (Windows, Google-Drive link on the app-use page — not yet pulled); it is a
  separate RE target relevant here.

## What supporting the X10 in `padtune` would require

1. **BLE transport** (e.g. `btleplug`) behind a `Transport` trait, alongside the
   existing USB-HID one — this is exactly the modularity the main session wants.
2. **Kr command layer**: frame `[len][opcode][content][SN]`, the `KrAgreement`
   opcodes, and the per-command content/response encoders (transcribe from the
   saved `*Req`/`*Rsp` classes).
3. Read-only bring-up on Linux: BlueZ scan for `QMacro`, connect, enable `FF02`
   notifications, send `97` (device info) / `49` (battery) and decode — before
   any write.
4. *(Optional shortcut)* test the USB-HID-on-iface0 hypothesis first; if it
   works, config could ride the existing hidraw transport with a Kr framing
   module and no BLE dependency.

The XInput-wired-lock is tracked separately and does not block config work.
